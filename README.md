# نظام مركز الكتاب — الإصدار 2.0.0

نظام إدارة حلقات التحفيظ (ملف HTML واحد + Supabase + PWA). الروابط:
- صفحة التعريف: `index.html` ← تفتح التطبيق على `/app/`
- التطبيق: `app/index.html` (مع `sw.js` و`manifest.json` والأيقونات)
- قاعدة البيانات: مجلد `sql/` (ملفات تُشغَّل مرة واحدة في Supabase)

## ما الجديد في 2.0.0

1. **إزالة Google بالكامل**: كل أزرار الدخول والتسجيل بـ Gmail، ودوال OAuth، وحقل البريد، والدخول بالإيميل. الدخول الآن باسم مستخدم وكلمة مرور فقط (كما كان).
2. **دخول آمن من جهة السيرفر مع بقاء الواجهة كما هي**:
   - كلمات المرور تُشفَّر بـ bcrypt داخل قاعدة البيانات، والـ hash **لا يصل للمتصفح أبداً**.
   - الهاش القديم (SHA-256) يُرقّى تلقائياً إلى bcrypt عند أول دخول ناجح للمستخدم.
   - جلسات برمز يصدره السيرفر (90 يوماً)؛ الدور والصلاحيات تُقرأ من السيرفر لا من التخزين المحلي.
   - **قفل مؤقت**: 5 محاولات خاطئة ← إيقاف 10 دقائق (يتضاعف حتى ساعتين مع التكرار)، ورسالة الخطأ لا تكشف هل الاسم موجود.
   - تغيير كلمة مرور حساب ينهي جلساته الأخرى؛ وحذف/تعطيل الحساب ينهي جلساته فوراً.
   - جدول `users` أُغلق عن الوصول المباشر؛ كل عمليات الحسابات (إنشاء/تعديل/حذف/موافقة/تسجيل) تمر عبر دوال سيرفر تتحقق من الصلاحية والمركز.
3. **الموظفون والصلاحيات** (للمشرف): إعدادات المركز ← «الموظفون والصلاحيات». الموظف يدخل من شاشة دخول المشرف نفسها ويرى فقط ما تسمح به صلاحياته.
4. **سجل التعديلات** (للمشرف): من أضاف/عدّل/حذف ماذا ومتى (طلاب، حلقات، معلمون، سجلات، موظفون، استيراد نسخ).
5. **تنبيه التحديث + رقم الإصدار**: يظهر رقم الإصدار في شاشة الدخول والإعدادات، وتنبيه «يتوفر تحديث» عند نزول نسخة جديدة.
6. **تذكير النسخ الاحتياطي الأسبوعي** للمشرف والمعلم (يمكن تأجيله يوماً).

كلمات مرور المعلمين والطلاب **تبقى ظاهرة للمعلم/المشرف كما هي** (محفوظة على جهازه فقط ولا تُرفع للسيرفر؛ السيرفر يحتفظ بالـ hash فقط).

## خطوات النشر (الترتيب مهم)

1. **Supabase ← SQL Editor ← New query**: الصق `sql/01_security_setup.sql` كاملاً ثم Run. آمن ولا يكسر النسخة القديمة، ويمكن تكراره.
2. **حدّث المستودع** بطريقة `apply-zip` (انظر «التحديث من الجوال» أدناه). إن فتحت النسخة الجديدة قبل الخطوة 1 ستظهر رسالة «شغّل ملف 01_security_setup.sql».
3. افتح التطبيق: المالك والمشرفون يدخلون **مرة واحدة من جديد** (الجلسات القديمة بلا رمز). المعلمون والطلاب لا يتأثرون.
4. **اختبر**: دخول المالك، مشرف، معلم، طالب، وإضافة طالب.
5. **Supabase ← SQL Editor**: شغّل `sql/02_lockdown.sql` (إغلاق الوصول المباشر). أعد الاختبار. عند أي مشكلة: `sql/99_rollback_lockdown.sql` يعيد الوضع السابق فوراً.
6. **Supabase ← Authentication ← Providers**: عطّل Google.
7. **حسابات Google القديمة**: شغّل `sql/00_diagnose.sql` (الاستعلام الرابع يسرد الحسابات بلا كلمة مرور). هؤلاء لا يستطيعون الدخول حتى يُعاد تعيين بياناتهم:
   - مشرف: المالك ← لوحة المالك ← «تعديل» على المركز.
   - معلم: المشرف ← إعدادات المركز ← 🔑 بجانب الحلقة.
   - طالب: المعلم ← بيانات الطالب ← 🔑.

## الصلاحيات

| الصلاحية | تسمح بـ |
|---|---|
| `students` | إضافة/تعديل/حذف الطلاب وحساباتهم وبيانات دخولهم |
| `records` | تسجيل الحضور والتسميع (فردي وجماعي) وحذف السجلات وإنهاء اليوم |
| `halaqat` | إضافة/تعديل/حذف الحلقات وبيانات دخول المعلمين |
| `teachers` | قبول أو رفض طلبات المعلمين الجدد |
| `reports` | عرض التقارير وتصديرها |
| `messages` | الرسائل والشكاوى |
| `backup` | تصدير واستيراد النسخ الاحتياطية |

لا تُفوَّض أبداً: إعدادات المركز (الاسم/الشعار/كلمة المرور المحلية)، إدارة الموظفين، سجل التعديلات.

## حدود الأمان المتبقية (للشفافية)

- **مُغلق الآن**: جدول `users` (لا قراءة ولا كتابة مباشرة)، حالة المركز وحذفه وإنشاؤه، الجلسات، سجل التعديلات.
- **ما زال يعتمد على سياسات RLS الحالية عندك**: جداول `halaqat` و`students` و`records` و`messages`؛ لأن التطبيق يستخدم المفتاح العام بدون Supabase Auth، فلا يستطيع السيرفر التمييز بين مستخدم وآخر عند القراءة/الكتابة المباشرة. تطبيق الصلاحيات على هذه الجداول في الواجهة فقط (تُمنع الأزرار) بينما تُفرض في السيرفر على الحسابات والموافقات والموظفين والسجل.
- إغلاقها بالكامل يحتاج إمّا Supabase Auth أو سياسات RLS مبنية على رمز الجلسة (وقد تؤثر على Realtime). شغّل `sql/00_diagnose.sql` وأرسل لي النتيجة لأصمم هذه المرحلة على سياساتك الفعلية.
- المزامنة الآن تفاضلية (ترفع المتغيّر فقط)؛ إذا عدّل جهازان **السجل نفسه** فآخر كتابة تفوز.

## التحديث من الجوال (apply-zip)

أول مرة فقط: أنشئ في المستودع الملف `.github/workflows/apply-zip.yml` (Add file ← Create new file) والصق محتواه.
كل تحديث: ارفع الـ zip إلى جذر المستودع ← Actions ← «Apply uploaded zip» ← Run workflow ← اكتب اسم الـ zip ← انتظر العلامة الخضراء ← افتح التطبيق وحدّثه مرتين وتأكد من رقم الإصدار.
الـ workflow يستبدل كل ملفات المستودع بمحتوى الـ zip (ما حُذف يُحذف) عدا مجلد `.github`، ويحذف الـ zip بعد التطبيق.

## ما اختُبر قبل التسليم

- ملف SQL على PostgreSQL 16 (بحالتي عمود `role` نصي وENUM): أكثر من 70 تحقق.
- 66 تحقق تكامل: التطبيق كاملاً يعمل على قاعدة PostgreSQL حقيقية بعد الإغلاق وبدور `anon` كما يفعل Supabase — دخول المالك/المشرف/المعلم/الطالب، الجلسات، القفل، التسجيل والموافقات، إنشاء الحلقات والطلاب، تغيير بيانات الدخول، الحذف، الموظفون والسجل، المزامنة التفاضلية، الدخول بلا إنترنت.
- ما لم أستطع اختباره: مشروعك الحقيقي على Supabase (لذلك وُضعت خطوة الاختبار قبل الإغلاق وملف التراجع).
